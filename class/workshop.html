El resultado del taller

Terminás cuando podés enseñar una pregunta, una fuente y una comprobación. La instalación depende de tus cuentas, permisos y experiencia: no tiene una duración garantizada.

  • Demo identificada como ficticia.
  • Negocio delimitado por IDs, moneda y zona.
  • Acceso privado con contraseña y passkey.
  • Una fuente real conciliada con su origen.

El kit es para un dueño por instalación. No es una plataforma multiempresa con roles. Antes de agregar equipos, diseñá permisos y aislamiento.

01 · Creá tu copia y abrí la demo

  1. Abrí el repositorio y elegí Use this template → Create a new repository. Elegí una copia privada si vas a sumar configuración interna.
  2. Instalá Git y una versión compatible de Node.js 22.22 o posterior. Abrí la terminal de tu editor y comprobá node --version y npm --version.
  3. En tu copia, botón Code: copiá su URL. Clonala y abrí esa carpeta en Claude Code o Codex. No pegues el ejemplo literal: reemplazá TU_USUARIO y TU_REPO.
git clone https://github.com/TU_USUARIO/TU_REPO.git
cd TU_REPO
npm ci
npm run demo:setup
npm run doctor
npm run dev

Abrí http://localhost:4321. Dejá esa terminal abierta. Comprobá la etiqueta DEMO, cambiá períodos y probá los tres estilos. demo:setup no sobrescribe una configuración existente. Los comandos de este bloque funcionan también en PowerShell.

Para ver esta clase: en otra terminal dentro del repo, npm run class:serve; abrí 127.0.0.1:4324.

02 · Definí tu negocio antes de conectar

Editá business.config.ts: nombre, moneda admitida, zona IANA, productos Stripe y cuentas/campañas Meta exactos. Las claves van en variables privadas, nunca acá. Si una cuenta contiene dos negocios, filtrá por IDs comprobados; no por importe o descripción.

NegocioPreguntaEvento de valor posible
Software¿Llega al primer resultado?Generó su primer proyecto útil
Curso¿Aplica lo que aprende?Completó el ejercicio clave
Consultoría¿Avanza la entrega?Completó un hito aceptado

Definí si el evento se cuenta por persona o por acción y qué significa “activado”. Un login no prueba valor. El kit trae product.activated y product.failed; nuevas métricas necesitan contrato, cálculo y pruebas.

03 · Prepará el acceso real

Usá una base Postgres dedicada, separada del sistema que cobra a tus clientes. Configurá en privado .env.local: APP_MODE=live, DATABASE_URL y APP_ORIGIN=http://localhost:4321 para esta prueba local. Para conexiones remotas, verificá TLS/certificado y permisos con el proveedor.

npm run db:setup
npm run auth:setup
npm run doctor -- --database
  1. db:setup instala el esquema de eventos. auth:setup instala el de acceso y pide usuario y contraseña de al menos 14 caracteres en terminal privada.
  2. Abrí .auth-bootstrap de forma privada: contiene un token de alta que vence a los 30 minutos. No lo copies a un chat ni a una grabación.
  3. Reiniciá el servidor después de cambiar variables. En /login, completá el alta y registrá la passkey. El dispositivo puede pedir rostro, huella o PIN; el servidor recibe una firma, no tu biometría.
  4. Borrá el archivo bootstrap después del alta. Cerrá sesión y comprobá que contraseña sola no alcanza para leer el tablero/API. Probá con el dispositivo físico.

Recuperación: npm run auth:setup -- --reset revoca todas las sesiones y passkeys anteriores. Se usa desde infraestructura controlada, no para saltear el segundo paso. El panel no registra una segunda passkey independiente: probá la sincronización o transferencia compatible del proveedor y documentá recuperación.

doctor comprueba configuración/esquema; no certifica permisos de Stripe/Meta ni tu Face ID. Leé la guía de seguridad.

04 · Conectá una fuente y conciliá

Usá credenciales de lectura con el mínimo alcance que el proveedor permita. Guardalas en .env.local o el gestor privado del hosting. No uses prefijos públicos, no las pegues al agente y no compartas capturas de secretos. Una clave expuesta se rota.

FuenteQué hayQué falta comprobar
StripeFacturas saldadas y MRR nominal del catálogoProductos, estados, fechas, descuentos/créditos; no equivale a banco o beneficio
MetaGasto y clics de campañas permitidasToken, versión soportada, moneda, zona y alcance
ProductoImportación JSON o sincronización PostHogMapeo, identidad pseudónima, cobertura, límites
EmailImportación JSON de entrega/clicAdaptar exportador; subject_id identifica mensaje, no destinatario

Seguí integraciones para variables y comandos vigentes. No configures las cuatro fuentes a la vez. El kit lee; no cobra, modifica anuncios ni envía emails.

Seleccioná un día cerrado y contrastá con el origen usando exactamente moneda, zona, fechas y filtros. Documentá diferencias. Una importación reciente no prueba historia completa. — significa dato no disponible; cero requiere medición.

05 · Importá eventos con identidad y cobertura

Ejemplo completamente ficticio para entender el formato. No lo importes a una base real como si fueran tus clientes. coverage declara la ventana completa exportada: inicio incluido, fin excluido. No uses la primera/última fecha de los eventos como evidencia de exhaustividad.

{
  "source": "product",
  "coverage": {
    "from": "2026-10-01T00:00:00Z",
    "to": "2026-10-02T00:00:00Z"
  },
  "events": [{
    "id": "ejemplo:accion-001",
    "kind": "product.activated",
    "subject_id": "usuario-pseudonimo-001",
    "occurred_at": "2026-10-01T15:00:00Z"
  }]
}

Guardá tu exportación real fuera del repositorio público y ejecutá:

npm run data:import -- /ruta/privada/eventos.json

Mismo ID y mismo contenido: no duplicar. Mismo ID con otro contenido: investigar conflicto. No cambies IDs para esconder errores. Respetá el límite del importador vigente y el recorte de cobertura. Reimportar o sincronizar manualmente no instala una rutina automática; si necesitás programación, configurala y monitoreala explícitamente.

Dejá pasos y evidencia de lo comprobado.
Quiero adaptar solo la apariencia del dashboard: nombre [nombre], color principal [color] y estilo [preferencia]. Conservá legibilidad, estados de error, definiciones y controles de acceso. Inspeccioná los tres estilos actuales antes de editar. No cambies fórmulas ni integraciones. Mostrame el diff y comprobá el resultado en los tamaños que usa el dashboard.

Revisá mi instalación sin mostrar secretos: configuración, scope, cobertura, acceso a páginas y API, variables públicas, recuperación, backups y dependencia de UTMify. Ejecutá doctor y las comprobaciones pertinentes. Separá implementado de probado. No publiques ni canceles servicios. Entregá hallazgos concretos y una prueba para cada corrección.

07 · La prueba que autoriza confiar

  1. Demo: etiqueta visible, tres estilos y períodos.
  2. Scope: producto/campaña ajenos quedan afuera.
  3. Eventos: reimportar no duplica; un conflicto se rechaza; siete días no aparentan noventa.
  4. Fuente real: mismo período cerrado, zona, moneda y filtros que el origen.
  5. Acceso: navegador sin sesión bloqueado; contraseña sin passkey no da datos; logout invalida sesión.
  6. Recuperación y backup: una restauración comprobada en entorno aislado; nunca sobre producción por probar.
npm run doctor
npm run typecheck
npm test
npm run build

Un build correcto no prueba un proveedor real ni un dispositivo físico. Anotá qué probaste, cuándo, con qué alcance y qué queda sin verificar. Si algo falla, no quites autenticación ni agregues datos demo para que “funcione”.

08 · Local no es producción

Para usarlo desde cualquier lugar necesitás hosting compatible, Postgres, variables privadas y un dominio HTTPS. Revisá la guía del repo antes de desplegar. Definí el origen definitivo antes de registrar la passkey: está ligada al dominio y no se traslada automáticamente desde localhost.

El servidor local se enlaza a loopback. Publicar requiere configurar el runtime/puerto del proveedor; no significa dejar tu computadora abierta. En el dominio final repetí login, API bloqueada sin sesión, passkey física, logout, conciliación y manejo de fallos. Protegé también hosting, GitHub y base con MFA y roles mínimos.

Nombrá un responsable de actualizaciones, cambios de API, rotación de claves, backups y avisos de fuentes caídas. La caché breve reduce lecturas repetidas; no reemplaza histórico, conciliación o monitoreo.

¿Entonces puedo cancelar UTMify?

No por haber instalado este kit. Puede reemplazar un uso puntual de tablero si las fuentes están conciliadas. Hoy no captura y conserva un recorrido UTM completo, no une anuncio con venta y no envía pixel/CAPI. Si dependés de esas funciones, mantené esa capa hasta tener un reemplazo probado.

  1. Inventariá reportes, scripts, checkout, conversiones e histórico.
  2. Compará en paralelo durante una ventana representativa de tu ciclo de ventas.
  3. Explicá diferencias y resolvé pagos tardíos, devoluciones y duplicados que apliquen.
  4. Prepará exportación y vuelta atrás; comprobá costos y funciones críticas.

UTMify declara tracking server-side y su ayuda documenta dependencia de UTMs/scripts y casos sin rastreo. Eso no constituye una auditoría de su implementación interna. Fuentes consultadas por el proyecto el 27/10/2026: sitio oficial, ventas no rastreadas y precios.

Leé la comparación completa y completá la lista de decisión. No se propone cancelar nada en el taller.

Costo propio = hosting + base + APIs + backups + mantenimiento + migración.
Costo actual = plan + extras + trabajo operativo.
Compará factura, moneda, impuestos y tiempo con el mismo criterio. No hay un ahorro universal.
